01

What Is Version Control?

Picture this: you have been building your first program or website for hours. You finally get it working, try one more improvement, and suddenly nothing works. This is the problem that version control was built to solve.

Think of version control as an undo history for your whole project, with checkpoints you choose to save. If a new change breaks your program, you can look back at an earlier checkpoint and recover the version that worked. In Git, saving one of these checkpoints is called making a commit. Saving a file in your editor updates the file; making a commit records a checkpoint in Git. Git cannot recover an edit it never recorded just because you pressed Save.

What Exactly Gets Tracked?
A commit is a saved project checkpoint: a snapshot of the files Git is tracking, with a message, names, email addresses, and dates. Git links these checkpoints into a history you can revisit. The recorded names and emails come from settings; they are labels, not proof of who wrote the code.

The Problem Without Version Control

Without version control, beginners commonly fall into patterns like these:

  • Saving files as project_final.py, project_final2.py, project_FINAL_v3_actually.py
  • Accidentally overwriting working code with broken experiments
  • Having no way to tell what changed between two versions
  • Sharing code through email or USB drives — a collaboration nightmare

Why It Matters for Every New Coder

Whether you are completing a class project, making a portfolio website, analyzing data, or contributing to an open-source project, your work will grow and change. Version control lets you experiment safely, restore known-working versions, share your progress, and build the workflow expected in software teams.

02

Understanding Git

Git is a free, open-source version control system created by Linus Torvalds in 2005, who also created the Linux kernel. Git can keep project history on each person's computer and exchange checkpoints between copies; this is what distributed means. Local tasks such as committing, branching, and viewing downloaded history work without internet access. A remote is another repository Git can exchange history with, such as a copy on GitHub. Reaching GitHub requires a network connection.

Think of a repository, or "repo," as your project plus its Git history. In a typical local project, git init creates a hidden folder named .git to keep that history and Git's settings. The files you open and edit are called the working tree. Git records the checkpoints you commit, rather than automatically recording every file save.

Key Mental Model
Git keeps local history and can exchange commits with other repositories. You can work offline and upload your saved checkpoints later; that upload is called a push. New files enter normal Git tracking when you stage them, and changes enter commit history when you commit them.

Core Concepts

Three Zones You Must Know

Zone Description Relevant Command
Working Directory Where you edit files. New files are untracked until staged; edits to tracked files are modifications. —
Staging Area (Index) The selection for your next checkpoint. Like choosing photos for an album, you choose the versions to include. Later edits need staging again. git add filename
Repository Your saved checkpoints and Git's settings. Each commit records the staged version and has an ID you can use to find it. git commit -m "message"
⚠ Common Beginner Mistake
With a plain git commit, unstaged edits are left out. If there are no staged changes, Git normally refuses to create a commit. Save your file, stage the intended version with git add, and review it with git diff --staged. If you edit it again after staging, stage it again to include those newer edits.
03

Understanding GitHub

GitHub is an online hosting and collaboration platform for Git repositories. When you push a local Git repository to GitHub, you create an online copy you can access from another computer and share with teammates, teachers, reviewers, or future employers when appropriate.

GitHub adds a social and collaborative layer on top of Git. You can browse code, open issues (like bug reports), review changes before they're merged, and contribute to projects happening anywhere in the world — including the open-source software that powers most of what you use daily.

Key Mental Model
If Git is the engine of a car, GitHub is the road network and GPS. Git stores and manages your history. GitHub gives that history a place to live online and makes it shareable, browsable, and collaborative.

What GitHub Adds

  • Remote hosting — pushed commits are stored online. Uncommitted files and local commits you have not pushed remain on your machine.
  • Pull Requests (PRs) — a formal way to propose code changes and request review before merging.
  • Issues & Project Boards — built-in task tracking. You can file bug reports, feature requests, and track what's in progress.
  • GitHub Actions — workflows you configure to run tests, build code, or deploy an app on events such as pushes or pull requests.
  • GitHub Pages — static website hosting from a repository; availability depends on your plan and repository visibility.
  • GitHub Codespaces — a hosted development environment accessible through your browser or VS Code, subject to usage limits and billing.
GitHub Is Not the Only Option
Git repositories can also be hosted on services such as GitLab, Bitbucket, or a self-hosted platform. The fundamental workflow — commits, branches, remotes, pushes, and pulls — remains Git.

Git vs GitHub — The Clear Distinction

This is probably the most common source of confusion for beginners, and it's worth making the distinction crystal clear before going further.

Git
  • Software installed on your computer
  • Local commits and history work offline
  • Free and open-source (GPLv2-licensed)
  • Manages version history locally
  • No account or login required
  • Command-line tool with many graphical clients
  • Created by Linus Torvalds, 2005
GitHub
  • A website and cloud service
  • Requires internet access
  • Free public and private repos; features vary by plan
  • Hosts Git repositories online
  • Public repositories can be read without an account
  • An account is needed to publish or contribute
  • Has a full web interface + features
  • Founded 2008; acquired by Microsoft 2018
Aspect Git GitHub
Type Software (CLI tool) Web platform / service
Internet required? No for local tasks; yes to contact an online remote Yes
Main purpose Track changes locally Share, collaborate, backup
Collaboration Built-in branches, merges, and exchange of commits Core feature (PRs, Issues, Forks)
Storage location Your machine The cloud
Learning curve Steeper (command-line) Gentler (visual UI + CLI)
Can exist without the other? Yes — Git works standalone You can use GitHub's browser tools without a local Git installation
The One-Sentence Summary
Git records project history and exchanges commits. GitHub hosts repositories and adds collaboration tools. Git works without GitHub, and GitHub's browser tools work without installing Git locally.
05

Essential Commands

You can control Git from a terminal (PowerShell, Terminal, Git Bash, or another shell) or through VS Code. Learning the small command-line vocabulary below makes every visual tool easier to understand.

Install and Set Up Git Once

Install a current Git version from git-scm.com, then configure the name and email recorded in your commits. These are author details, not GitHub sign-in credentials. The git init -b examples require Git 2.28 or later.

bash — Setup
# Verify that Git is installed git --version # Tell Git your name and email git config --global user.name "Your Name" git config --global user.email "you@example.com" # Use main as the first branch name in new repositories git config --global init.defaultBranch main # Confirm your settings git config --global --list user.name=Your Name user.email=you@example.com init.defaultbranch=main
Privacy Before Your First Commit
Commits can expose your configured email when a repository is public. If you prefer privacy, copy your exact noreply address from GitHub's email settings and use it in git config --global user.email before committing. Changing this setting does not rewrite earlier commits.
Terminal Note
The terminal examples use Git Bash on Windows or a Bash-compatible shell on macOS or Linux. Copy commands only, without the displayed $ prompt or sample output. PowerShell has different shell syntax and file encodings; you can create and save the files in VS Code and run the Git commands separately. Replace example usernames, repository names, and filenames with your own. Your commit IDs and output may differ from the examples.

Starting a Repository

bash — Initialize
# Create a new project folder and initialize Git mkdir my-project cd my-project git init -b main Initialized empty Git repository in ~/my-project/.git/
# OR clone an existing repo from GitHub git clone https://github.com/username/repo-name.git

The Daily Loop — Add, Commit, Push

After editing and saving files, stage the intended changes, commit locally, and push when ready to share them. This example assumes a tracked main.py, a current branch named main, and a writable remote named origin. The first-push setup follows below.

bash — Daily Loop
# Step 0: See what's changed git status On branch main Changes not staged for commit: modified: main.py
# Step 1: Stage the files you want to commit git add main.py # Alternative: stage additions, edits, and deletions under this directory git add .
# Step 2: Commit with a clear, descriptive message git commit -m "Add user input validation to main.py" [main 3f4a1c2] Add user input validation to main.py 1 file changed, 12 insertions(+), 2 deletions(-)
# Step 3: Push to GitHub (sync to remote) git push origin main Enumerating objects: 5, done. To https://github.com/username/my-project.git

Stage means "select for the next checkpoint." Staging does not move your original files. git add . selects eligible new files, edits, and deletions in the current folder and its subfolders; it skips ignored new files. Review that selection before committing. git push origin main uploads the saved history of the branch named main, even if you are currently working on another branch.

First Push from a New Local Repository

After making a local commit, create an empty repository on GitHub and choose its visibility. For this path, leave the README, license, and .gitignore initialization options off, because your local repository already has its own history. If you started by cloning a GitHub repository, origin is already configured; skip git remote add.

bash — First push (local branch is main)
git branch --show-current main git remote add origin https://github.com/you/my-project.git git remote -v git push -u origin main

A remote is another repository whose address Git remembers, often your copy on GitHub. Think of origin as a contact name for that address; it can point to GitHub or another host. -u sets an upstream: the remote branch paired with your local branch for later pushes and pulls. If your branch has a different name, use that name consistently. See GitHub's first-push instructions.

Signing In to Push
For HTTPS, use an approved credential helper, GitHub CLI's browser sign-in, or a personal access token with the necessary access. Your GitHub account password is not accepted for Git operations over HTTPS. SSH is another option after configuring a key. Never put credentials in the remote URL. See GitHub's authentication guide.

Viewing History & Differences

bash — History
# See history reachable from the current branch git log # Compact one-line version (much easier to read) git log --oneline 3f4a1c2 Add user input validation 7a2b3d1 Initial commit
# See what changed in your files (not yet staged) git diff # See what's staged but not yet committed git diff --staged

Pulling Changes From GitHub

Commit your intended work before pulling, and use git status to check that your working tree is clean: there are no pending changes to commit. Ignored files can still be present.

bash — Pull
# Start with a clean working tree, then update local main git switch main git pull --ff-only origin main Already up to date. # Or if teammates pushed new code: Updating 7a2b3d1..9f1e5b3 Fast-forward README.md | 4 ++++

Think of git fetch as bringing new checkpoints home so you can inspect them: it downloads remote history and updates Git's record of the remote branches, without changing your working files. git pull fetches and then brings a remote branch's changes into the branch you are currently working on. A fast-forward simply moves your branch to a newer checkpoint on the same path. If you and a teammate both added separate checkpoints, --ff-only stops so you can decide how to combine the two paths.

A merge brings changes from two paths together. Another method, rebase, replays your committed changes on a different starting checkpoint, usually creating replacement commits. Follow your team's chosen method; plain git pull behavior depends on settings, options, and Git version. The branching section below walks through a merge; Git's rebasing guide explains the alternative and its precautions.

VS Code Source Control: A Visual Way to Use Git

VS Code includes Git integration in its Source Control view and uses your installed Git for local repositories. Install Git and configure your name and email first. Open Source Control with Ctrl+Shift+G (Control+Shift+G on macOS as well). The editor and terminal use the same repository.

Your First Commit in VS Code

1
Open a project folder
Use File > Open Folder. Source control works on the entire folder, not just a single open file.
2
Initialize the repository
Open Source Control and choose Initialize Repository if the folder is not already tracked.
3
Edit and review
Changed files appear under Changes. Select a file to inspect additions and deletions in the diff editor before saving a checkpoint.
4
Stage and commit
Select + beside the files for this checkpoint, write a clear message, and select Commit.
5
Publish or sync
Use Publish to GitHub for a new hosted repository, or Publish Branch to upload a branch to an existing remote. Use Sync Changes to pull then push a branch with an upstream.
Good Beginner Habit
Always review the changed lines before committing. A commit should contain one understandable improvement, not every unsaved experiment from the day.

Branch indicatorgit branch / git switchSee or change your current line of work.

Publish a New Folder to GitHub

  1. Make one local commit first so the repository has something meaningful to publish.
  2. For a repository with no remote, select Publish to GitHub in VS Code and sign in when asked. The status-bar Publish Branch action can offer this path when no remote exists.
  3. Choose visibility deliberately: keep private work private unless you intend to share it publicly.
  4. Open the new repository on GitHub and check that your files and commit history are present.

See the official VS Code source-control quickstart. Available labels and actions can vary with repository state and settings.

Real-World Workflow

Knowing individual commands is one thing. Understanding how they fit into a coherent workflow is what separates someone who "knows Git" from someone who can actually use it productively on a team.

Your Personal Project Workflow

For an assignment, portfolio project, experiment, or learning exercise, this sequence covers the daily essentials:

1
Create or publish a repository on GitHub
Go to github.com, click "New", name your repo, choose Public or Private, add a README. This gives you a remote home for your project before you even write code.
2
Clone it to your machine
git clone https://github.com/you/repo.git creates a local checkout and configures origin. Then enter it with cd repo or open that folder in VS Code.
3
Write code, then commit frequently
Do not wait until the entire project is complete. Commit after meaningful progress: "Add contact form layout" or "Fix off-by-one error in loop." Small commits make history readable.
4
Push to GitHub regularly
Push your commits after each work session. A successful push preserves that branch's committed work on the remote; it does not upload uncommitted edits, ignored files, or every other local branch.
5
Share only when ready
A repository link can show a teacher, teammate, or reviewer your files and progress. Check visibility and remove secrets before sharing a public link.

When Other People Contribute

For team projects, update main with a clean working tree before creating a feature branch. Work and commit on that branch, push it with git push -u origin feature/add-login, and open a pull request. Pulling updates the branch you have checked out; it does not automatically update every branch. Bring newer main changes into a feature branch using your team's merge or rebase policy.

Writing Good Commit Messages

Your commit message is a note to your future self (and your teammates). Here's how to write ones that actually help:

Commit message examples
❌ Bad commit messages — useless history git commit -m "stuff" git commit -m "fix" git commit -m "asdfghj"
✅ Good commit messages — tells a story git commit -m "Add input validation for user age field" git commit -m "Fix index out of bounds in search function" git commit -m "Refactor printReceipt to reduce code duplication"
Commit Message Convention
Use the imperative mood: "Add feature" not "Added feature" or "Adding feature." Think of it like completing the sentence "This commit will… your message here."

Branching & Merging

Imagine trying a new idea on a side path from a saved checkpoint. That is what a branch lets you do: build a separate line of history while the original branch keeps its saved version. Technically, a branch is a name pointing to a commit; creating one does not duplicate the whole project. Switching branches usually updates the files in your working folder to the chosen branch's version.

The initial branch name depends on your Git configuration or the host's settings. This guide uses main, selected explicitly with git init -b main; other repositories may use master or another name. Create a feature branch, a branch for a particular change, and commit there. When ready, merge it to bring its changes into the project's shared branch. A branch named main is a convention, not a guarantee that the code works.

The diagram shows a merge commit after both branches advanced. If main has not advanced since the feature branch started, Git can usually fast-forward it to the feature's latest commit without creating a merge commit.

Uncommitted Work and Branches
Commit or safely stash your edits before switching branches. Uncommitted edits can carry over to another branch; Git may instead refuse to switch if doing so would overwrite them. A new branch does not automatically save or isolate unsaved or uncommitted work.

Branch Commands

bash — Branching
# In an existing repository with commits, list local branches git branch * main
# Create and immediately switch to a new branch git switch -c feature/add-login Switched to a new branch 'feature/add-login'
# Create and save login.py in your editor, then commit it git add login.py git commit -m "Implement basic login function"
# Switch back to main git switch main
# Merge the feature branch into main git merge feature/add-login Updating a1b2c3d..e4f5a6b Fast-forward login.py | 1 + 1 file changed, 1 insertion(+)
# Clean up — delete the local branch after merging git branch -d feature/add-login
What Is HEAD?
Think of HEAD as Git's "you are here" bookmark. It usually names your current branch, which points to its latest checkpoint. A new commit advances that branch; switching branches changes where the bookmark points. Opening an older commit directly can put you in detached HEAD: the bookmark points to that commit instead of a branch.

When a Merge Conflict Happens

Git may pause when it cannot combine changes automatically, such as conflicting edits to the same lines or an edit on one side and deletion on the other. VS Code provides inline actions and a merge editor for text conflicts. Edit the result deliberately, remove conflict markers, test the result, and stage every resolved file before completing this merge with a commit. Use git status to see what remains; git merge --abort cancels an in-progress merge.

Merge conflict — inspect, edit, commit
# Example markers for a text conflict <<<<<<< HEAD Welcome to my portfolio ======= Welcome to our project >>>>>>> feature/update-heading
# After editing the file to the correct final text: git add index.html git commit -m "Resolve homepage heading conflict"

Protect Your Project with .gitignore

A .gitignore file specifies patterns for untracked files Git should ignore during ordinary staging. It does not stop tracking files already in the index. Create it early and commit the file to share the patterns with teammates; a user can still force-add an ignored file, so these rules are not access controls.

Privacy Rule: Secrets Do Not Belong in GitHub
Never commit API keys, passwords, access tokens, private keys, cloud credentials, or configuration files containing secrets. A database connection string may include a password; an .env file may contain credentials. Public repositories can be copied quickly, and deleting a secret later does not make an exposed credential safe again.

What .gitignore Does and Does Not Do

It Helps With It Does Not Do
Preventing new matching files from being staged accidentally. Removing a file already committed or pushed to GitHub.
Keeping dependencies, generated builds, and local settings out of history. Encrypting files or making the folder private on your computer.
Sharing a repository rule with teammates through a committed .gitignore. Guaranteeing that editors, extensions, or AI tools cannot read ignored files.

A Beginner-Friendly Starter File

Use patterns appropriate to your project. Keep a safe example configuration file, such as .env.example, with placeholder values so other people know what settings they need.

.gitignore - commit this safety file
# Secrets and local configuration .env .env.* !.env.example *.pem *.key credentials.json
# Dependencies, virtual environments, and generated output node_modules/ .venv/ __pycache__/ dist/ build/
# Local operating system clutter .DS_Store Thumbs.db Desktop.ini

Check Before Every Commit and Push

terminal - privacy check
git status --short --ignored # Explain why a file is ignored git check-ignore -v .env # Inspect the exact contents about to become history git diff --staged # If .env was already tracked, add an ignore rule, then stage its removal git rm --cached .env

git rm --cached .env leaves the local file on disk and stages its removal from the tracked snapshot. Commit that removal along with the ignore rule. Earlier commits still contain it. git check-ignore normally skips tracked files, and a diff may not show binary file contents; inspect the staged filenames as well as the diff.

If a Key Was Committed
Treat it as exposed: revoke or rotate the key immediately, remove it from future commits, and follow your platform's guidance for cleaning repository history. Adding it to .gitignore alone is not a fix.

For the official procedures, read GitHub's Ignoring files guide and Removing sensitive data from a repository guide.

Safe AI-Assisted Coding Workflow

AI tools can explain code, suggest tests, and help debug, but they also process the files or text you allow them to see. Use AI as a coding partner only after you have decided which information is safe to share.

Important Distinction
.gitignore excludes matching untracked files from ordinary Git staging. It does not prevent an AI tool from reading them. An exclusion setting may control indexing or suggestions without restricting filesystem access; check the tool's actual capabilities and permissions.

Set Boundaries for AI Tools

  1. Create .gitignore before asking an assistant to build or publish a project.
  2. Keep real keys in ignored local files or a secret manager; give the assistant a placeholder-only .env.example.
  3. Use the tool's supported exclusions and permissions. If it must not read sensitive files, keep those files outside its accessible workspace or enforce filesystem restrictions; an ignore pattern or written instruction alone is not an access boundary.
  4. State the rule directly in your request: do not open, quote, edit, stage, or commit secret-bearing files.
  5. Before committing AI-generated changes, review the diff yourself and run the Git privacy checks from the previous section.
prompt - safety instructions for an AI assistant
Work only with source files needed for this task. Honor .gitignore and do not read or edit .env, keys, tokens, credentials, or private data. Use .env.example with placeholders when configuration is needed. Before proposing a commit, show which files changed and flag anything sensitive.

When You Intentionally Need an Ignored File

An ignored file is not automatically unsafe. Generated logs, test output, or large local data may be ignored simply because they do not belong in Git history. If an AI tool needs information from one of these files, provide a small sanitized excerpt or explicitly allow only the non-sensitive path. Do not tell an assistant to ignore every .gitignore rule across the workspace, and never override ignore rules for a secret just to make an AI workflow easier.

Responsible Workflow
AI may generate code; you remain responsible for reviewing what leaves your machine, what enters Git history, and what is published to GitHub.

Fix Common Beginner Problems

When Git reports a problem, do not delete the repository and start over. Read git status first: it usually names the state you need to fix.

What You See What It Means First Safe Step
fatal: not a git repository The terminal is in the wrong folder, or Git was never initialized there. Open the correct project folder; use git init only for a new repository.
nothing to commit or no changes added to commit There is no new staged snapshot to commit. The working tree may be clean, or edits may be unstaged or ignored. Save your file and inspect git status. Stage the intended changes if there are any.
Push rejected as non-fast-forward The remote branch contains history your local branch does not include. Fetch and inspect the correct branch. Try git pull --ff-only with its upstream configured; if histories diverged, follow the team's merge or rebase policy. Do not force-push as a routine fix.
Authentication or permission error while pushing Credentials, repository access, or a branch rule may prevent the push. Check the remote URL, sign-in method, write access, and any requirement to submit a pull request. Pulling does not fix permission errors.
Wrong file is staged The file is selected for the next commit, but no work is lost. After an initial commit, use git restore --staged filename. Before the first commit, use git rm --cached -- filename for a newly staged file. Both leave the working file on disk.
Secret or generated file appears in Changes The file should probably not be recorded in history. Add an ignore pattern for an untracked file. If it is already tracked or staged, also remove it from the index with git rm --cached. Rotate exposed credentials and assess history cleanup.
Unstage and Discard Are Different
git restore --staged filename changes the index and keeps your working file. git restore filename replaces a tracked working file with its index version, discarding unstaged edits. Check the diff and save any work you need before discarding it.
Never Commit Secrets
Do not commit passwords, API keys, access tokens, private keys, or environment files containing secrets. A .gitignore file prevents untracked files such as .env and build output from being added accidentally; it cannot erase a secret already committed and shared.

# Example .gitignore entries; use only patterns relevant to your project .env node_modules/ __pycache__/ build/
# Review what Git will include before committing git status git diff --staged

Practice Lab: Publish Your First Repository

Build a small repository with four meaningful commits, starting with an ignore rule that protects local secrets. Complete it with the terminal, with VS Code Source Control, or by switching between both views so you see that they describe the same Git history.

1
Create and initialize
Create a folder named git-practice-lab, initialize Git, and add a .gitignore before making project files.
2
Make four checkpoints
Make separate commits for .gitignore, README.md, learning notes, and a README update describing what you practiced.
3
Publish and verify
Use VS Code's Publish to GitHub, or follow the first-push steps above with an empty remote. Choose visibility deliberately and verify all four commits online.
bash — Practice lab checkpoints
mkdir git-practice-lab cd git-practice-lab git init -b main echo ".env" > .gitignore git add .gitignore git commit -m "Add ignore rule for local secrets" echo "# Git Practice Lab" > README.md git add README.md git commit -m "Add README"
echo "Things I learned about Git" > notes.txt git add notes.txt git commit -m "Add learning notes" echo "## What I Practiced" >> README.md git add README.md git commit -m "Document practice steps" git log --oneline
You Have Finished When
You can explain the difference between local commits and GitHub, identify your four commits in history, review a change in VS Code, and publish or push without exposing secrets.
